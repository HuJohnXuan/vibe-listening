# Vibe Listening：从互动网页到完整产品的后端分析

> 调研日期：2026-10-17
>
> 范围：现有项目架构、高星开源媒体服务与可渐进接入方案。本文是项目分析，不创建账号体系、数据库、对象存储或管理后台。

## 结论

现在的 Vibe Listening 是一个**本地优先的沉浸式播放器**，不是一个多用户音乐产品：用户音频、收藏、歌单、场景、队列和偏好都保存于当前浏览器的 IndexedDB；部署在 Vercel 的页面没有 API、服务端数据库、身份系统、对象存储或任务队列。

这不是“少一个后台页面”这么简单。完整产品至少要补齐三层：

```text
用户端（Vibe Listening）
  ↕ 账户、曲库、播放与场景 API
产品后端（鉴权、业务规则、任务、审计）
  ↙                    ↘
PostgreSQL（关系数据）   对象存储（用户音频和封面）
                           ↕
                    异步 Worker（解析、波形、转码）
```

管理后台建立在这套系统之上，用于看见用户、曲库、上传任务、存储与风险状态；它不能替代数据服务本身。

## 当前事实与缺口

| 领域 | 当前事实 | 成为完整产品后的缺口 |
| --- | --- | --- |
| 身份 | 无账号；浏览器即用户边界 | 登录、设备会话、账号删除与数据导出 |
| 音频 | `Blob` 保存在 IndexedDB，仅当前设备和浏览器可用 | 文件对象存储、上传、权限校验、配额、断点续传 |
| 曲库 | 浏览器本地解析标签、SHA-256 去重 | 服务端曲库索引、跨设备同步、版本与冲突处理 |
| 个人状态 | 收藏、歌单、队列、场景在 `app-state` store | 用户维度的数据模型、读写 API、迁移规则 |
| 播放 | HTML Audio 直接读取本地 Blob/演示资源 | 受鉴权的流式 URL、播放历史、失败和带宽观察 |
| 运维 | 无 | 上传任务、扫描/解析状态、异常、审计、成本与存储监控 |

当前本地结构并非废弃资产。`Track`、`LocalAppState`、歌单、场景和统一队列已经是合适的领域模型雏形；关键是把 UI 直接读 IndexedDB 的方式改成可替换的数据访问边界。

## 用户真正需要完成的事（JTBD）

**【事实】** 用户希望每个人能上传自己的歌，并认为当前页面缺少后台数据，整体不像完整产品。

**【推断】** 当用户在另一台设备、另一个浏览器或一段时间后回来时，他想重新进入自己的听歌空间、曲库和场景，而不重新导入、重新整理和重新配置；同时产品拥有者想看见系统是否可靠地接收、保存和服务这些内容。

所以首个后端目标不应是“做一个管理员能看到所有歌的后台”，而应是：**让用户拥有可验证的账号、曲库和跨设备状态，同时让运营者能处理失败和成本。**

## 推荐目标架构：托管产品后端 + 本地缓存

推荐采用“云端为账号与资料真相来源，本地为播放和离线缓存”的混合模式。它保留 Vibe Listening 的私密、快速和沉浸体验，又能补上产品能力。

```text
浏览器
  ├─ 现有 Three.js 房间、播放器与 IndexedDB 缓存
  ├─ Auth：登录、设备会话
  ├─ API/BFF：曲库、歌单、场景、播放状态
  └─ 直传：签名 URL → 私有对象存储
                         ↓
                 上传任务 / 元数据解析 Worker
                         ↓
       PostgreSQL ← 音频 Asset、Track、用户状态、任务状态
                         ↓
              管理后台（用户、任务、存储、审计）
```

### 为什么不是“Next.js API 直接接收 100MB 音乐文件”

当前单首允许到 100MB。把文件先传到 Vercel/Next.js 再转存会带来请求体限制、超时、重复带宽和难以恢复的失败。因此应当由后端先创建上传记录、授权和短期签名 URL，浏览器把文件直接上传到私有对象存储；Worker 再异步读取并解析。前端只轮询或订阅任务状态。

### 建议的基础设施组合

| 能力 | 首选实现 | 原因 |
| --- | --- | --- |
| Web 与 BFF | 保留 Next.js + Vercel | 现有前端无需换栈，负责会话与轻量 API。 |
| 账号 | 托管 Auth（如 Supabase Auth、Clerk 或 Auth.js + 自建库） | 首期避免自行实现密码、找回、会话撤销和邮件验证。最终选型前需核算价格与地区合规。 |
| 关系数据库 | PostgreSQL | 适合用户、曲库、歌单、场景、历史和审计间的关系查询。 |
| 音频/封面 | 私有 S3 兼容对象存储（R2/S3 等） | 大文件、私有访问、签名下载和生命周期策略是成熟能力。 |
| 异步任务 | 独立 Worker + 队列 | 解析封面、时长、哈希、波形和可选转码都不阻塞上传请求。 |
| 管理后台 | 同一 Next.js 项目中的 `/admin`，仅管理员角色 | 能复用设计系统、鉴权和 API；不急于单独新建后台项目。 |

这里的“托管”是实现路径，不等于把用户音乐公开给平台。音频对象必须私有，播放 URL 短时有效，并按用户/库归属检查。

## 对历史 FastAPI 匿名状态方案的判断

仓库内已有 `openspec/changes/add-anonymous-user-data-backend/`。它提出 FastAPI + 单机 JSON 文件 + `X-Device-Id`，只保存收藏、Later、播放历史和少量偏好。该方案没有实施。

| 设计点 | 判断 | 原因 |
| --- | --- | --- |
| UI → service → adapter 的边界 | 保留 | 这是让本地实现、测试实现和云端实现能替换的必要前提。 |
| 乐观更新、失败后仍可本地使用 | 保留 | 弱网或服务故障不能让房间和播放器失效。 |
| 健康检查、严格 CORS、非敏感日志 | 保留 | 是服务上线的基本运维边界。 |
| 匿名 `X-Device-Id` | 不作为产品身份 | 它是可复制的客户端能力标识，不是登录、授权或找回机制。 |
| 单机 JSON 文件 | 不采用 | 无法可靠处理多人、事务、索引、备份、并发和跨设备。 |
| 旧的固定 IP / `sslip.io` 部署 | 不采用 | 当前产品已在 Vercel，且生产域名、证书、密钥和可观测性应独立管理。 |
| 仅同步演示曲目 ID | 不足 | 一旦用户导入私有音频，服务端必须能识别 asset、library 和归属。 |

所以，历史方案可以作为“API 分层和离线降级”的参考，不能作为当前产品后端的实施蓝本。

## P1 的最小 API 轮廓

P1 不上传音乐，只同步轻数据。接口应以当前用户会话识别身份，不能由前端传 `userId` 决定归属。

| 用例 | API 语义 | 冲突处理 |
| --- | --- | --- |
| 登录后拉取资料 | `GET /v1/me/profile-state` | 返回服务端版本号和 `updatedAt`。 |
| 收藏 | `PUT` / `DELETE /v1/me/favorites/{trackId}` | 幂等；服务端以用户 + 曲目为唯一键。 |
| 歌单 | `GET/POST/PATCH/DELETE /v1/me/playlists` | 歌单内容含稳定项 ID 与排序位置；冲突时返回版本不匹配而非静默覆盖。 |
| 场景 | `GET/POST/PATCH/DELETE /v1/me/scenes` | 场景只存偏好和关联歌单 ID，不存音频或私密记忆。 |
| 续播 | `PUT /v1/me/playback-state/{deviceId}` | 每台设备单独写当前位置；账户级“继续播放”由服务端选择最新有效状态。 |
| 数据导出/删除 | `POST /v1/me/export`、`DELETE /v1/me` | 异步任务；删除需确认与审计。 |

P1 的曲目引用要分两类：

- `catalogTrackId`：产品内置演示曲目，所有用户都可解析。
- `localFingerprint`：只存在某个设备的本地文件指纹；其他设备只显示“需要重新导入”，绝不把它映射成相同标题的另一首歌。

这能让歌单和场景先跨设备同步，又不假装本地文件已经存在于另一台设备。

## P2 上传与播放的状态机

```text
创建上传记录
  → 浏览器直传私有对象存储
  → 完成通知
  → Worker 校验 MIME / 大小 / 哈希
  → 解析元数据与封面
  → ready 或 failed
  → 授权后取得短时播放 URL
```

| 状态 | 用户可见结果 | 管理后台要显示 |
| --- | --- | --- |
| `uploading` | 上传进度，可取消或恢复 | 上传者、大小、过期时间。 |
| `processing` | “正在读取歌曲资料”，不可播放 | Worker 阶段、排队时长。 |
| `ready` | 可加入播放队列和歌单 | 格式、时长、哈希、存储占用。 |
| `failed` | 不进入曲库，显示可理解原因 | 机器错误码、可重试性、原始诊断。 |
| `deleted` | 从用户视图消失 | 删除者、时间、延迟清除时间。 |

服务端不应在首版“自动抓取歌曲信息或下载音频”。用户上传的文件、内嵌元数据和用户手动编辑才是来源；第三方资料补全需要独立的授权、来源和隐私评估。

## 管理后台信息架构（首版）

```text
运营后台
├─ 概览：上传成功率、失败任务、存储增长、播放错误
├─ 用户：账号状态、设备、库用量、支持工单关联
├─ 上传任务：队列、阶段、失败原因、安全重试
├─ 曲库资产：只看元数据与对象状态，不默认试听/下载
├─ 存储与配额：按用户/类型统计、待清理对象
├─ 举报与审计：下架、申诉、管理员操作记录
└─ 系统配置：功能开关、公告、受控环境声预设
```

这套后台的重点是“可解释”和“可恢复”。例如用户说“歌上传了但播放器找不到”，支持人员应能从用户 → asset → upload job 找到失败阶段，而不是靠查日志或读取原始音频。

## 从现有代码到 P0 的改造边界

当前 `useMusicLibrary` 直接调用 `music-library.ts`，`useLocalAppState` 直接调用 IndexedDB。P0 只需要增加抽象，并不改动 3D 房间、统一队列、环境声或住客。

```text
现在
  UI hook → IndexedDB adapter

P0 之后
  UI hook → Library/Profile Repository interface
                ├─ IndexedDB repository（当前默认）
                └─ Remote-sync repository（P1 后启用）
```

P0 完成标准：本地模式的自动测试和体验不变；可在测试中替换 repository；不出现半成品登录入口、空后台或未配置的云端请求。

## 最小数据模型

### 内容与存储

| 实体 | 核心字段 | 说明 |
| --- | --- | --- |
| `users` | `id`, `email`, `role`, `created_at`, `deleted_at` | 不将 email 当业务主键。 |
| `libraries` | `id`, `owner_id`, `name`, `quota_bytes` | 为后续家庭/团队库留出边界，首期每人一库即可。 |
| `assets` | `id`, `library_id`, `object_key`, `sha256`, `size`, `mime_type`, `status` | 文件事实来源；`status` 为 uploading / processing / ready / failed / deleted。 |
| `tracks` | `id`, `asset_id`, `title`, `artist`, `album`, `duration`, `cover_asset_id`, `metadata_version` | 仅在 asset ready 后可播放。 |
| `upload_jobs` | `id`, `asset_id`, `stage`, `error_code`, `started_at`, `finished_at` | 可回答“为什么这首歌没进曲库”。 |

### 用户状态

| 实体 | 核心字段 | 当前本地模型的对应物 |
| --- | --- | --- |
| `favorites` | `user_id`, `track_id`, `created_at` | `favoriteTrackIds` |
| `playlists` / `playlist_items` | `owner_id`, `name`, `position`, `track_id` | `Playlist` |
| `scenes` | `owner_id`, `name`, `room_preferences`, `ambient_preferences`, `playlist_id` | `ListeningScene` |
| `playback_state` | `user_id`, `device_id`, `queue`, `current_track_id`, `position`, `volume`, `updated_at` | `PlayerState` |
| `listening_events` | `user_id`, `track_id`, `event_type`, `occurred_at`, `position` | 新增；用于续播与分析，不替代实时状态。 |
| `device_sync` | `device_id`, `user_id`, `last_synced_at`, `app_version` | 新增；避免两台设备静默互相覆盖。 |

**私人记忆默认继续只在设备端。** 它不进入服务端模型，除非未来用户明确选择“同步我的私人记忆”，并提供删除与导出能力。

## 管理后台应如何设计

首版后台只服务运营与排错，不做内容编辑器。

| 模块 | 首版要回答的问题 | 首期操作 |
| --- | --- | --- |
| 概览 | 活跃用户、成功上传、失败任务、存储增量是否异常？ | 查看趋势和告警，不改用户内容。 |
| 用户 | 某用户为什么无法播放或超出配额？ | 查账号状态、库大小、设备数；禁用/恢复账号需审计。 |
| 曲库与上传 | 文件在哪个步骤失败？有没有重复或无法识别的编码？ | 查 `upload_jobs`、重试安全任务、查看元数据和对象状态。 |
| 存储 | 成本是否可控？是否有未引用对象？ | 按用户/类型统计；执行经确认的清理任务。 |
| 内容安全与举报 | 用户是否报告了侵权或滥用？ | 处理举报、下架对象、保留审计记录。 |
| 系统设置 | 环境声预设、功能开关、公告是否可控？ | 管理只读配置与 feature flag，不直接改数据库。 |
| 审计 | 谁在何时访问或修改了什么？ | 搜索管理员操作和关键状态变化。 |

管理后台的权限至少分为 `admin`、`support`、`user`。支持人员不应能直接下载所有用户音频；下载、删除、配额调整和账号封禁需要理由与审计。

## 分阶段迁移路线

### P0：为后端留接口，不改变用户体验

- 将 `music-library.ts` 的直接 IndexedDB 调用抽成 `LibraryRepository` 接口。
- 将 `useLocalAppState` 抽成 `ProfileRepository` 接口。
- 为曲目、歌单、场景和队列补齐服务端可用的 UUID、更新时间和版本字段。
- 增加匿名设备 ID 与同步状态，但不上传音频。

验收：现有本地模式仍可离线运行；没有登录时无功能回退。

### P1：账号与“轻数据同步”

- 接入登录、PostgreSQL 和 row-level ownership。
- 仅同步收藏、歌单、场景、房间偏好和播放续播状态；音乐文件仍在设备本地。
- 提供“本机数据是否同步成功”、退出登录、账号删除和导出状态。

验收：同一账号两个浏览器能看见同一歌单/场景；文件不存在时明确显示“此设备尚未导入”，不错误播放别的歌曲。

### P2：用户云端曲库

- 创建私有对象存储、签名直传、可恢复上传与 `upload_jobs`。
- Worker 解析元数据、封面、时长与内容哈希；先不做服务端转码。
- 用短时签名播放 URL 取代公开静态文件；保留 IndexedDB 缓存作为加速层。
- 引入配额、失败重试上限、对象删除延迟和数据导出/删除流程。

验收：上传中断后可恢复；不同用户无法访问彼此的音频 URL；后台能定位每次解析失败。

### P3：完整产品运营能力

- `/admin` 的用户、上传任务、存储、举报和审计模块。
- 事件流和基础指标：激活、首歌导入成功率、7 日回访、播放成功率、上传失败率、每活跃用户存储量。
- 需要时加入异步波形、歌词导入、媒体转码和多设备冲突策略。

验收：运营人员可排查一次真实用户问题，不需直接查数据库或读取用户音频；所有敏感操作可审计。

### P4：可选的“连接自托管音乐服务器”

将 Navidrome/Subsonic 或 LMS 作为高级用户的**外部数据源**，而不是 Vibe Listening 的核心后端。先从只读导入目录、歌单和封面开始；播放、令牌保存和权限隔离要单独评估。

## 优先级判断（ICE，均为推断）

| 候选 | Impact | Confidence | Ease | 推荐 |
| --- | ---: | ---: | ---: | --- |
| P0 数据访问边界 | 9 | 9 | 8 | 先做；它决定后续是否可迁移而不重写 UI。 |
| P1 登录 + 轻数据同步 | 9 | 8 | 6 | 第一项面向用户的后端能力。 |
| P2 私有云端曲库 | 10 | 6 | 3 | 价值最高，但涉及存储、带宽、版权与任务系统，应在 P1 验证后启动。 |
| 首版管理后台 | 6 | 8 | 6 | 与 P2 同步做最小排错后台，不独立抢在用户数据前。 |
| 服务端转码/音频相似度 | 4 | 4 | 2 | 暂缓；成本和复杂度高。 |
| Navidrome/LMS 兼容 | 3 | 4 | 2 | 高级用户候选，不影响主线。 |

## 需要先确认的产品决策

1. 用户音乐是否真的要上传到云端，还是仅同步歌单、场景和偏好？这是成本、版权和技术路径的分叉点。
2. 目标用户是“每人私有曲库”还是“可分享/协作的家庭或社区空间”？后者需要分享、授权和举报体系。
3. 首发是否只面向中国大陆用户？会影响登录、对象存储地域、支付和隐私告知的选择。
4. 是否需要运营后台由你亲自使用，还是先只需工程排错台？这决定后台的产品化程度。

在上述问题明确前，最稳妥的下一步是 P0 的数据访问边界和 P1 的“账号 + 不上传音频的轻数据同步”原型；它能让产品开始像产品，又不会提前把用户音乐和云存储成本带进来。
