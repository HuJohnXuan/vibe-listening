## Context

当前应用是 Next.js/React 客户端播放器，歌曲元数据和音频 Blob 已通过 `vibe-listening-music` IndexedDB 的 `songs` store 保存；当前播放、Later、收藏、房间手动状态仍主要在页面内存中。播放使用单个 HTMLAudioElement，Three.js 房间已有三种变体、住客路径和减少动态效果处理。详见 `proposal.md` 与六份能力规格。

已有历史后台方案与当前本地优先边界冲突。本设计只扩展浏览器本地数据和客户端行为，不复用该后台方案。

## Goals / Non-Goals

**Goals:**

- 用一份稳定、可测试的播放器状态模型连接音频元素、队列、曲库和界面。
- 在不丢失现有歌曲 Blob 的前提下升级 IndexedDB，持久化组织数据和场景。
- 复用现有页面骨架、Three.js 场景和浏览器原生音频能力，以最少新增模块实现规格。
- 让阶段 A、B 各自可运行、可迁移、可回退，并保留实机验收证据。

**Non-Goals:**

- 不接入账号、服务器、跨设备同步、在线音源、下载或搜刮。
- 不把私人记忆、原始路径或音频内容写入场景与播放器状态。
- 不做完整家具沙箱、养成系统、插件市场、复杂交叉淡化或精确节拍识别。
- 不在本变更中承诺阶段 C 的 PWA、歌词、系统媒体控制或完整备份候选。

## Decisions

### 1. 以稳定歌曲 ID 和显式队列状态作为单一播放事实源

新增纯 TypeScript 队列模型，至少包含 `trackIds`、`currentIndex`、`mode` 和在随机模式生成后固定的 `shuffleOrder`。UI 操作先更新模型，再由播放器控制器解析当前 Track；`ended` 只调用队列的 next 转移。

选择这一方式是因为现有 Track ID 已稳定，本地歌曲使用内容哈希，且可把模式边界写成纯函数测试。不会建立事件总线或额外状态库；React hook 足以承载当前页面规模。

### 2. IndexedDB 升级为同库多 store，保留 `songs`

提升数据库版本，继续使用现有 `songs` store，并新增单记录 `playerState`、`favorites`、`playlists`、`scenes` 等逻辑所需 store。迁移只创建新 store，不重写音频 Blob；所有结构包含 `schemaVersion`，读取时过滤不存在的歌曲 ID。

相比 localStorage，IndexedDB 可统一处理结构化数据、错误和未来容量；相比引入 Dexie，原生封装已存在，当前操作简单，不值得增加依赖。播放进度采用节流写入，并在暂停、切歌和卸载可用节点补写。

### 3. 曲库整理以派生视图实现

搜索、标签筛选、收藏过滤和最近加入排序都从已加载 Track 列表及持久关系派生，不复制歌曲数据。歌单只存元数据和有序稳定 ID。删除关系与删除音频分离，所有破坏性曲目删除继续沿用现有明确入口。

### 4. 场景保存稳定设置，不保存运行瞬间

将 `ListeningRoom` 当前散落的房间、光线、天气、住客显示/活动状态提升为受控 `RoomPreferences`，由页面传入并接收变更。场景快照引用这些稳定设置、可选 playlist ID 和 ambient mix。恢复场景只更新空间和偏好；播放关联歌单使用独立按钮。

不保存镜头角度、角色坐标、正在进行的动作或当前歌曲，避免 Three.js 内部状态与数据 schema 耦合。

### 5. 环境声复用 HTMLAudioElement 并由单控制器淡化

初版每次只激活一条循环环境声，用独立 HTMLAudioElement、音量状态和短时 `requestAnimationFrame` 淡化；不构建 Web Audio 多轨图。素材按房间选择并带来源清单。视觉天气与声音开关分离，用户选择的联动设置才允许场景恢复时启用。

若许可合适的素材不能随仓库分发，先交付控制和自带的程序化/原创短循环，不能用来源不明文件填充。

### 6. 住客优化留在既有状态机

扩展 `createResident` 的行为状态和过渡，不另建动画框架。指令在移动中替换 pending 目标，挥手记录并恢复此前行为；天气、播放状态只触发低频候选，不覆盖用户指令。视觉优化复用程序化几何、现有服装材质和房间生成器。

### 7. UI 延续桌面双栏并使用按需面板

房间继续占主视觉；曲库、歌单、队列和场景放入现有侧栏内的清晰分段或切换面板，底部播放控制保持可达。新增按钮使用原生语义元素、可见焦点和 `aria-pressed`/标签；拖动场景时继续阻止物件误触。

重要视觉变化先以真实页面原型/本地运行截图验收，确认后再完成细节。该步骤不改变能力规格，只决定表现参数。

## Risks / Trade-offs

- [浏览器存储升级错误可能影响已有音频] → 迁移只增 store，使用 fake-indexeddb 覆盖从 v1 升级和 Blob 保留，并在生产构建前人工使用旧库快照验证。
- [队列、当前曲和 audio 事件互相触发造成竞态] → 队列转移集中为纯函数，`ended`/手动切歌共享入口，失败跳过设置一轮上限。
- [频繁保存进度造成不必要写入] → 固定间隔节流，并只在关键生命周期事件补写。
- [环境声素材带来许可或包体问题] → 每项记录来源许可，限制数量和码率；无可靠许可则不分发该素材。
- [Three.js 视觉优化增加 GPU 负担] → 优先调布局、颜色和已有几何，限制新网格/粒子，保留 30 FPS、后台跳过和 reduced-motion 路径。
- [一次改动范围较大] → 按任务顺序先建立数据/状态层，再逐块接 UI；阶段 A 完整通过后再接阶段 B，避免同时改动所有流。

## Migration Plan

1. 先为队列和新持久化结构补纯逻辑与 IndexedDB 升级测试。
2. 发布阶段 A 代码时自动把 DB 从 v1 升级到新版本；旧歌曲保持原样，新状态为空或从当前默认值建立。
3. 接入队列、整理和恢复 UI，完成 A-01 至 A-09 浏览器验收后再推进阶段 B。
4. 阶段 B 先接受控房间偏好和场景数据，再加入许可明确的环境声，最后完成住客/房间视觉细节。
5. 若升级失败，应用继续以当前内存状态播放并显示保存失败；回滚代码不得执行数据库删除，较新 store 可留存等待修复版本。
6. 全部验收后更新 `ARCHITECTURE.md`、`DATA_MODEL.md`、`TESTING.md`、README 和迭代基线的实现状态。

## Open Questions

- 环境声最终素材文件与署名会在素材任务中按许可证选择；这不改变控制行为或任务结构。
- 房间细节的最终色值、远景轮廓和动作幅度将在真实页面预览时微调，不改变已确认角色外形与规格。
